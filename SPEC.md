# Spec: Audio Fetch - Legacy to Electron-Vite Migration

**Spec Version**: 2.0
**Last Updated**: 2026-08-12
**Status**: Approved
**Review**: Second-pass audit against current repository and `legacy/`

## Review Baseline

Current repository state:

- Electron-Vite scaffold only.
- `src/main/index.ts`, preload bridge, and generic renderer demo exist.
- Audio Fetch services, IPC handlers, config service, test infrastructure, and migration-specific assets do not yet exist.
- `package.json` does not yet include `youtube-dl-exec`, `@ffmpeg-installer/ffmpeg`, Vitest, or Playwright.
- Existing CI workflows still target the Python/PySide6 application.
- `legacy/` remains the behavioral reference during migration.

This document defines the target. It does not claim the target is already implemented.

## Locked Decisions

1. **Queue**: One download may run at a time. A new download while one is active returns a busy error; no concurrent execution and no FIFO backlog in v1.
2. **Cookies**: Support Chrome, Chromium, and Brave on Windows and Linux. Firefox and Edge are excluded from the migration scope.
3. **Configuration**: Use a new Electron configuration schema. Do not read, migrate, or promise compatibility with legacy config files.

## Objective

Migrate Audio Fetch from the Python desktop application (PySide6 + embedded FastAPI) to an Electron application using electron-vite, TypeScript, and Node.js while preserving all in-scope user-visible behavior and the legacy UI appearance.

### Target Users

- End users on Windows and Linux downloading YouTube audio.
- Single-user desktop usage; no multi-user server mode.

### In Scope

- YouTube video information lookup.
- Audio format and quality selection.
- Three-tier download fallback behavior.
- Chrome-family browser cookie extraction.
- Single-active-download protection.
- Custom frameless title bar and window controls.
- New JSON configuration stored in Electron's user-data directory.
- 8-bit UI sound behavior generated by the renderer audio module.
- Windows installer and Linux AppImage/deb packaging.

### Non-Goals

- macOS support.
- Firefox or Edge cookie extraction.
- Concurrent downloads.
- Legacy config-file migration.
- New user-facing features or intentional UI redesign.
- Performance work beyond migration requirements.
- Replacing the legacy application during this draft/specification phase.

### Success Summary

The migration is successful when the Electron application passes the functional, security, test, and packaging criteria in this document, and the in-scope legacy workflows remain behaviorally equivalent.

### Runtime Data

Use Electron APIs, not hardcoded platform paths:

- Config: `path.join(app.getPath('userData'), 'config.json')`.
- Logs: `app.getPath('logs')` or a child directory under `app.getPath('userData')`.
- Single-instance protection: `app.requestSingleInstanceLock()`; no user-managed `app.lock` file.

### Module Boundaries

- **Main**: downloads, external binaries, file I/O, config, logging, cookies, queue, system integration.
- **Preload**: explicit, typed IPC methods only.
- **Renderer**: DOM, UI state, user interactions, Web Audio effects.
- Renderer never receives Node.js or filesystem access.

## Functional Contract

### Video Information

- Validate the input before invoking the main process.
- Return title, uploader, duration, thumbnail URL, supported formats, and supported qualities.
- Preserve the legacy format set: `mp3`, `m4a`, `opus`, `wav`, `best`.
- Preserve the legacy quality set: `0` = 320 kbps, `5` = 192 kbps, `9` = 128 kbps.

### Download Behavior

- Use best available audio as the source.
- Preserve legacy output conversion behavior for the supported formats.
- Preserve thumbnail conversion and embedding.
- Preserve metadata embedding.
- Sanitize output filenames for Windows and Linux.
- Perform external work asynchronously; keep the renderer responsive.

### Tier Strategy

The migration must preserve the tested legacy escalation contract:

1. **Tier 1**: up to three attempts: default request, browser user-agent, user-agent plus request delay/rate limiting.
2. **Tier 2**: browser-cookie authentication using the configured Chrome-family browser and its compatible profiles.
3. **Tier 3**: advanced mobile-client fallback, enabled only when configured.
4. Escalation signals include legacy auth/bot indicators and HTTP status codes `401`, `403`, and `429`.
5. Tier order, attempt counts, and user-visible failure handling must be covered by tests.

The legacy `TierStrategy` flag table and the runtime `download_audio_with_tiers` path contain different Tier 3 details. The exact Tier 3 flags require approval before implementation; the migration must not silently choose between them.

### Queue and Shutdown

- At most one download executes at any time.
- A second download request returns a user-facing busy error.
- Closing during an active download prompts for confirmation.
- Minimize, close, and title-bar drag work on Windows and Linux.
- A second application launch focuses the existing instance instead of opening another window.

### Browser Cookies

- Supported browsers: Chrome, Chromium, Brave.
- Supported OS: Windows and Linux.
- Firefox and Edge are rejected as unsupported, not silently treated as Chrome.
- Browser paths and profile discovery must be tested without requiring real user cookie databases.

### Configuration

The new schema is versioned and independent of the legacy schema:

```json
{
  "schemaVersion": 1,
  "downloads": {
    "defaultPath": "",
    "format": "mp3",
    "quality": "0"
  },
  "tierStrategy": {
    "browser": "chrome",
    "fallbackEnabled": true,
    "tier1Attempts": 3,
    "tier3Enabled": false
  },
  "ui": {
    "windowWidth": 850,
    "windowHeight": 650,
    "windowTitle": "Audio Fetch"
  },
  "logging": {
    "level": "WARNING",
    "maxBytes": 10485760,
    "backupCount": 3
  }
}
```

Requirements:

- Missing config uses defaults.
- Invalid config fails safely and falls back to defaults with a logged reason.
- Saving creates parent directories asynchronously.
- Legacy config keys and files are not read or migrated.

## Code Style

Follow the existing repository configuration unless this spec is explicitly amended:

- TypeScript strictness; avoid `any`; use `unknown` for untrusted errors.
- 2-space indentation.
- Single quotes.
- No semicolons.
- No trailing commas.
- Maximum line width: 100.
- `camelCase` functions/variables, `PascalCase` classes/types, `UPPER_SNAKE_CASE` constants, kebab-case filenames.
- Prefer `const`, async/await, narrow types, and small modules.
- Keep IPC channel names stable and explicit.

```typescript
function errorMessage(error: unknown): string {
  return error instanceof Error ? error.message : String(error)
}

async function fetchVideoInfo(url: string): Promise<VideoInfo> {
  try {
    return await videoInfoService.fetch(url)
  } catch (error) {
    logger.error('Failed to fetch video info', { url, error: errorMessage(error) })
    throw new Error(`Video info fetch failed: ${errorMessage(error)}`)
  }
}
```

## IPC Contract

Main handlers use `ipcMain.handle()`. Renderer calls only the typed preload API.

Required namespaces:

- `videoInfo.fetch(url)`.
- `download.start(url, options)`.
- `window.minimize()`.
- `window.close()`.
- `queue.getStatus()` for close confirmation and UI state.

The preload bridge must not expose raw `ipcRenderer`, Node.js modules, or arbitrary channel invocation.

## Boundaries

### Always Do

1. Validate URLs, browser names, config values, and output paths at trust boundaries.
2. Log external-call failures with context without logging cookies or secrets.
3. Keep renderer work non-blocking.
4. Use IPC for cross-process communication.
5. Preserve legacy HTML/CSS dimensions, states, text, and interaction flow unless approved otherwise.
6. Test all tier transitions, single-active-download behavior, cookie filtering, and close confirmation.
7. Use Electron path APIs and async filesystem operations.
8. Keep context isolation enabled and expose only narrow preload methods.
9. Run typecheck, tests, and lint before merge.

### Ask First

1. Adding or replacing dependencies.
2. Changing Tier 1/Tier 2/Tier 3 order, flags, attempt counts, or escalation rules.
3. Changing the preload/IPC API.
4. Changing the new config schema.
5. Changing Windows/Linux packaging targets or signing.
6. Adding Firefox/Edge support, concurrent downloads, macOS support, or legacy config migration.
7. Changing file paths, public behavior, or UI layout.

### Never Do

1. Commit secrets, cookies, tokens, or personal paths.
2. Use `any` to bypass type errors.
3. Enable `nodeIntegration`, expose raw `ipcRenderer`, or use remote eval.
4. Shell-interpolate untrusted URLs or filenames.
5. Use synchronous filesystem operations in production paths.
6. Bundle yt-dlp source or hardcode platform-specific user paths.
7. Remove tests or weaken assertions to make builds pass.
8. Claim Firefox/Edge, concurrent downloads, config migration, or macOS support.

## Approved Decisions

1. **Tier 3 implementation**: Follow the legacy runtime downloader path with `android` and `mweb` clients, without cookies. Tier 3 runs after Tier 2 exhaustion, uses one attempt per client in listed order, and escalates only on the existing auth/bot signals or HTTP status codes `401`, `403`, and `429`.
2. **Progress reporting**: Defer progress reporting until after functional parity. No progress IPC contract is required for migration v1.
3. **NES.css delivery**: Bundle NES.css for offline UI availability.
4. **Linux packaging extras**: Build only AppImage and deb targets.
5. **Windows signing**: Produce unsigned Windows builds. Code signing remains a release prerequisite if distribution requirements change.
6. **Package-manager authority**: Bun is authoritative. Use `bun.lock`; do not generate or commit an npm lockfile.

Resolved for this draft:

- Browser scope: Chrome/Chromium/Brave only.
- Queue: one active download, no concurrency.
- Config: new schema, no legacy migration.
- Logging default: `WARNING`.
- Metadata and thumbnail embedding: required.
